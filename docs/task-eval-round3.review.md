## 2. 补上用户体感延迟（改 `AIProxy/eval/run.mjs`）

现在 runner 只记**整次请求的总耗时**。但 App 是流式的：用户在确认面板里看到**第一条待办**时就觉得「有反应了」。思考型模型的特点恰恰是前面长时间一个字都不出。所以要多记两个时间点：

| 字段 | 含义 |
|---|---|
| `firstTextMs` | 发出请求 → 收到第一个 `text` 事件 |
| `firstTodoMs` | 发出请求 → 累计文本里**第一条待办完整出现**（一个完整的待办 JSON 对象闭合） |
| `totalMs` | 现有的总耗时，不变 |

- `firstTodoMs` 的判定尽量和 App 的流式解析口径一致（`Extractor/TodoExtractorService.swift` 的增量解析逻辑）。做不到完全一致时，用「`todos` 数组里第一个对象的括号闭合」近似，并在结果文档写明判定方法。
- 汇总里每个字段都给 P50 / P95 / 最大值；对比表（`--table`）加上 `firstTodo P50`、`firstTodo P95`、`>30s 条数` 三列。
- 旧的 `scored.json` 没有新字段时，表里显示「—」，不要报错。
- 改动只在 eval 目录内，不改 Worker 代码。先用 `--provider-file` 跑 1～2 条确认字段正确，再跑整轮。

## 4. 判定口径

### 4.1 能不能当主力（三条同时满足）

| 条件 | 标准 | 理由 |
|---|---|---|
| 准确率 | 73 条（白名单除外）**最多错 1 条** | 沿用轮 2 口径 |
| 首条待办 | `firstTodoMs` **P50 ≤ 5 秒、P95 ≤ 12 秒** | 用户等到「有反应」的时间 |
| 不超时 | `totalMs` **超过 30 秒的为 0 条**（含晚高峰复跑） | 生产超时 35 秒，超时就落「待解析」 |

晚高峰复跑（R1b/R2b）和白天那一次**分别**判定，两次都满足才算过。

### 4.2 结论怎么写

在结果文档里给出明确建议，四选一：

1. **air 过关、5.3-flash 不过** → 主力换回 air，5.3-flash 降为备线（或撤掉）。
2. **两者都过** → 选 `firstTodoMs` P50 更低的当主力，写清差距。
3. **只有 5.3-flash 过** → 保留现状，同时写清首条待办延迟的实测值，供产品负责人判断能否接受。
4. **都不过** → 列出每个模型差在哪一条；如果 R7（air 关闭思考）过了，单独标出来。

GPT 两组（R5、R6）只回答「能不能进入备选池」，不参与主力决定（它们走 OpenRouter，有地区封锁和额外延迟的问题，见轮 2 结论）。

**执行者只给建议，不改 `wrangler.toml`、不切生产主力**，由产品负责人拍板。
